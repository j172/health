## 3. `navLabel` 欄位與排序邏輯

1. 在 `ToolCatalogEntry`（`lib/server/tools/catalog.ts`）新增 `navLabel?: string`，只有需要跟
   SEO `title` 不同措辭時才填；未填則 Nav/Footer 退回用 `title`。67 個工具不用每個都填，只有
   你判斷「頁面 SEO title 跟 nav 上顯示的理想簡短名稱不一樣」的才需要填 `navLabel`。
2. 排序邏輯需要「中文字筆畫數」對照——**不要自己亂猜筆畫數**，也不需要為了這個引入整套大型
   筆畫函式庫；由於分類名稱與工具 `navLabel`/`title` 是有限、固定的字串集合，建議寫一個小型的
   「第一個字 → 筆畫數」對照表（只需涵蓋實際會用到的第一個字），或評估是否有現成、輕量的
   npm package（例如 `cnchar` 一類提供筆畫查詢的套件）值得引入——自行評估後選擇最簡單可維護
   的做法，並在 PR 描述中說明選了哪種做法、為什麼。
3. 排序函式要能同時用在「分類清單排序」跟「分類內工具清單排序」，兩處呼叫同一套邏輯，不要各自
   兜一份。

## 4. 驗收

- 全部工具都有明確分類歸屬，沒有遺漏；分類數量分布不要有任何一類佔比過度懸殊（原本
  public-facility 佔 36% 的情況不應該在新分類裡重演）。
- 5 組合併都確實變成單一 route，舊 slug 都設定 301 重導向到新 slug（可用 `curl -I` 驗證
  status code）。
- Nav/Footer 顯示的分類與工具順序符合筆畫排序規則（英文項目在前）。
- `navLabel` 欄位存在但不影響任何工具頁面的 `<title>`/meta/JSON-LD。
- `npm run build`、既有測試維持通過；新增/搬動的工具頁面本身功能不能壞掉（尤其合併後的分頁
  切換要能正確顯示原本兩邊的資料）。
- PR 描述附上完整的「舊 slug → 新 slug」對照表，方便使用者之後驗證重導向。
