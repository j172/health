## 1. Background

`lib/server/facilities/geocodeBatch.ts`'s `SOURCES_IN_PRIORITY` (22 entries, `lib/server/facilities/geocodeBatch.ts:55-87`) draws every address-only facility source from one shared daily budget across two live geocoding APIs — OpenCage (capped at 1,400/day by policy, `geocodeBudget.ts:22-25`) and Nominatim (capped at 1,000/day by policy, same lines). Only 3 sources were previously confirmed to bypass this budget entirely via a pre-geocoded government dataset (`scripts/backfill-facilities-from-opendata-geo.mjs`: kindergarten/`moe_kindergarten`, clinic/`nhi_hospital`, pharmacy/`nhi_pharmacy`).

On 2026-09-09, three high-backlog sources (`moenv_iaq_premise`, `moenv_cleaning_squad`, `moenv_green_hotel_epr`) had to be bumped to the front of the queue (`geocodeBatch.ts:56-64`) because larger sources ahead of them (pharmacy, clinic) were exhausting the whole shared daily budget before ever reaching them — they sat at 0 geocoded rows for days (issue #130). This document researches whether the other sources in the queue have a **structural** fix available (an open dataset that already carries coordinates, or a stable code that can be exactly matched against one) rather than a **priority-ordering** fix, and separately researches whether a better free geocoding fallback exists for whatever remains genuinely uncoverable by open data.

This is research only — see [§6 Explicit Non-Goals](#6-explicit-non-goals). No source code, cron schedule, or production data changed as part of this document.

### 2.1 Detailed findings, evidence, and citations

**#1 `iaq_premise` / `moenv_iaq_premise` — 室內空氣品質法公告場所 (researched, none found).**
Confirmed via `WebFetch` of the dataset's own schema page (https://data.moenv.gov.tw/dataset/detail/AQX_P_23) that `AQX_P_23` carries exactly 7 fields — `placeid, placename, statdate, zipcode, county, address, placetype` — matching what `scripts/import-moenv-iaq-premises.mjs:14-19` already documents. No latitude/longitude field, no institution code field, and no sibling MOENV dataset with coordinates for the same "公告場所" population turned up in search. This source genuinely depends on the live geocode budget.

**#2 `cleaning_squad` / `moenv_cleaning_squad` — 地方清潔隊 (researched, none found).**
`WebFetch` of https://data.moenv.gov.tw/dataset/detail/wr_s_04 confirms exactly 4 fields — `countycode, organizationname, organizationaddress, organizationtel` — matching `scripts/import-moenv-cleaning-squads.mjs:15-18`. No coordinate field, no code field. This is a small dataset (one row roughly per city/county cleaning team, not per township — the field is `countycode` not a township code), so its total backlog is inherently small; low priority for a structural fix, low cost to keep on live geocoding.

**#3 `green_hotel` / `moenv_green_hotel_epr` — 環保旅館(EPR_P_02) (cross-match candidate, not externally confirmed).**
`scripts/import-moenv-green-hotels.mjs:1-34` already pulls **two** MOENV datasets for the same `green_hotel` facilityType: `gp_p_43`（環保標章旅館環境即時通地圖資料）, which ships `latitude`/`longitude` directly (`import-moenv-green-hotels.mjs:11-19`, `sourceKey: "moenv_green_hotel"`), and `epr_p_02`（環保旅館推動計畫旅館名冊）, which does not (`import-moenv-green-hotels.mjs:21-30`, `sourceKey: "moenv_green_hotel_epr"` — the one actually in `SOURCES_IN_PRIORITY`). Both datasets describe overlapping populations of certified green hotels published by the same agency. This repo already has a proven pattern for exactly this shape of gap — the pharmacy exact-(name,address) cross-source match (see #14 below) — and the same technique (matching `epr_p_02` rows against the already-downloaded, already-coordinate-bearing `gp_p_43` rows by exact name+address, before falling back to live geocoding) is a same-cost, zero-new-external-call candidate. Not independently verified how much overlap exists between the two datasets' rosters in this research pass — worth measuring before committing engineering time.

**#4 `child_safety_spot` / `npa_child_safety_spot` — 婦幼安全警示地點.**
**Confirmed by reading the actual script**, not guessed from the filename: `scripts/backfill-child-safety-spots-geo.mjs:48-61` calls `https://nominatim.openstreetmap.org/search` directly with a 1.1s `setTimeout` throttle (`backfill-child-safety-spots-geo.mjs:129`) — a separate, uncoordinated Nominatim consumer outside `lib/server/facilities/geocodeBudget.ts`, exactly as `docs/specs/opendata-geo-scheduled-backfill.md:91-101` already documents. It also carries a small hand-maintained `LANDMARK_COORDS` table (17 entries, `backfill-child-safety-spots-geo.mjs:28-46`) and checks the production DB for an already-geocoded row with the same display name before calling Nominatim at all (`backfill-child-safety-spots-geo.mjs:76-85, 105-115`) — this is a caching/reuse layer, not a coordinate source. `scripts/import-npa-child-safety-spots.mjs` (the actual ingestion script, separate from the backfill script) confirms the NPA source dataset itself (`opdadm.moi.gov.tw` dataset `DBB18796-8A89-4917-B4AB-D0AF26FAFEDC`) ships no coordinates — `lat: null, lng: null` unconditionally (`import-npa-child-safety-spots.mjs:93-94`). Searched for an NPA-published coordinate version: only found a **Taipei-city-only** mirror (data.gov.tw `145628`, 臺北市婦幼安全警示地點, confirmed via `WebFetch` to have fields `編號、縣市別代碼、地點位置、管轄分局、郵遞區號、備註` — no lat/lon either) — not usable as a national coordinate source. Researched, none found at national scope; the description-string addresses in this dataset are also inherently hard to geocode (junction names, landmark references — see `backfill-child-safety-spots-geo.mjs:118-124`'s regex stripping of `與...路口`, `附近` etc.), so even a perfect address-point database would not fully solve this source.

**#9 `disability_welfare` / `mohw_disability_welfare` — 身障福利機構 (researched, none found).**
Fetched the actual CSV directly and confirmed its header: `機構名稱,縣市,鄉鎮市區,地址,連絡電話,機構類型,核定服務人數(住宿),核定服務人數(夜間),核定服務人數(日間),實際服務人數(住宿),實際服務人數(夜間),實際服務人數(日間),評鑑屆次,最近1次評鑑等第` (note: identical schema shape to elder_welfare's — both are SFAA-family "機構名冊" exports) — no lat/lon, no code field. Matches `scripts/import-mohw-disability-welfare.mjs:44-65`'s field usage.

**#10 `ltc_contracted` / `mohw_ltc_contracted` — 長照特約機構 (already has coordinates from source).**
`scripts/import-mohw-ltc-contracted.mjs:6-8` states explicitly in its own header comment: "already carries lat/lng so no geocoding backfill is needed for it." Confirmed by reading the mapping code: `lat: lat && lng ? lat : null, lng: lat && lng ? lng : null` sourced from the CSV's own `經度`/`緯度` columns (`import-mohw-ltc-contracted.mjs:106-121`), fetched from `ltcpap.mohw.gov.tw/publish/abc.csv`. **This source should not have been counted among the ~19 "fully dependent on the live API budget" sources** — any rows it contributes to the geocode queue are only those where the source CSV itself lacked lat/lng for that row, not the general case.

**#11 `long_term_care` / `mohw_ltc_full` — 長照機構 (already has coordinates from source).**
`scripts/import-mohw-facilities.mjs:69-91`'s `importLongTermCare()` reads `緯度`/`經度` columns directly from `ltcpap.mohw.gov.tw/public/csv/ltc.csv` (`toNum(r["緯度"])`, `toNum(r["經度"])`, lines 83-84). Same correction as #10 — this source already ships coordinates; it is not a genuine live-geocoding dependent.

**#12 `disability_atm` / `nfcc_accessible_atm` — 無障礙ATM (confirmed: hardcoded lookup table, not live geocoding, not a cross-dataset match).**
**Read the actual script, not guessed from the filename.** `scripts/backfill-nfcc-accessible-atm.mjs:50-68` defines `KNOWN_ATM_COORDS`, a **hardcoded JavaScript object literal with exactly 17 name→{lat,lng} entries**, manually curated (branch names like `"淡水一信馬偕護專"`). The main flow (`backfill-nfcc-accessible-atm.mjs:110-127`) builds each ATM's display name from the source CSVs (`nfcc.org.tw/data/commoncharge/atm_wheel_list.csv` / `atm_voice_list.csv`), looks it up in `KNOWN_ATM_COORDS`, and — critically — **any record with no match is filtered out before submission** (`recordsWithCoords = records.filter(r => r.lat != null && r.lng != null)`, line 129): there is no fallback to live geocoding or to any other coordinate dataset inside this script at all. This is neither "pre-baked coords" in the sense of a government dataset, nor live geocoding, nor a cross-dataset match — it is a small, manually-maintained allowlist that silently drops every unmatched ATM from this particular script's own submission, while the *other* path (the regular `disability_atm`/`nfcc_accessible_atm` entry in `SOURCES_IN_PRIORITY`, fed by the unified `geocodeBatch.ts`) is what actually carries the live-geocoding burden for every ATM branch not in that 17-entry table. Searched for an NFCC-published or credit-union-federation coordinate dataset for branch/ATM locations: none found — 中華民國信用合作社聯合社 does not appear to publish an open geospatial dataset for this.

**#13 `hakka_community` / `hakka_dtst20230600002` — 客委會伯公照護站 (researched, none found).**
Fetched the JSON directly (`https://cloud.hakka.gov.tw/Pub/Opendata/DTST20230600002.json`) and confirmed its exact shape: `city_name, CountyCode, No, Unit_name, Address` — `CountyCode` is an administrative-district code (e.g. `"106"`, `"334024"`), not an institution/business code, and there is no lat/lon field. Matches `lib/server/facilities/sources/hakkaCommunity.ts:12-16`'s own interface and its comment ("no coordinates... and no stable per-row ID").

**#14 `pharmacy` / `tfda_pharmacy` — 一般藥局 (partial solution already exists in this repo, underexploited).**
`lib/server/facilities/sources/tfdaPharmacies.ts:9-19` confirms TFDA's `data.fda.gov.tw/data/opendata/export/35/json` carries no lat/lon and no NHI-style institution code — only name/address/phone/`是否為健保特約藥局`. However, `lib/server/facilities/queries.ts:297-335` documents (and this research independently confirms by reading the code) that **an exact (name, address) match against `nhi_pharmacy`** — which already has coordinates via `scripts/backfill-facilities-from-opendata-geo.mjs`'s `backfillPharmacies()` (kiang/pharmacies GeoJSON, `sourceKey: "nhi_pharmacy"`) — already catches roughly 50/140 (~36%) of a sampled 200-row set (issue #132) and is used to **de-duplicate the search-result display**, but this is a query-time `ROW_NUMBER()` dedup (`queries.ts:311-322`), not a coordinate backfill: the underlying `tfda_pharmacy` row in the database still has `lat = NULL`. The exact same (name, address) match key that already proves ~36% overlap could be applied at backfill time (the same pattern `backfill-facilities-from-opendata-geo.mjs` already uses for kindergarten/clinic/pharmacy) to write real coordinates onto the matched `tfda_pharmacy` rows, removing roughly a third of this source's backlog from the live geocode budget with **zero new external calls** (the `nhi_pharmacy` GeoJSON is already downloaded by the existing script). The remaining ~64% (pharmacies not NHI-contracted) still need to be geocoded.

**#15 `health_check` / `mol_labor_checkup` — 勞工健檢機構 (strong cross-match candidate, high confidence).**
Fetched the live payload from `apiservice.mol.gov.tw/OdService/download/A17000000J-020057-8CT` directly and confirmed a `醫療機構代碼` field with value `"0101090517"` for 臺北市立聯合醫院. This is the **same 10-digit format** as the `id` property in `raw.githubusercontent.com/kiang/info.nhi.gov.tw/master/docs/geojson/hospitals.json` (confirmed by fetching that GeoJSON directly: e.g. `"id": "0138010027"` for 衛生福利部南投醫院) — the same GeoJSON `scripts/backfill-facilities-from-opendata-geo.mjs:158-175`'s `backfillHospitals()` already downloads and indexes into a `codeMap` for the unrelated `clinic`/`nhi_hospital` source. Both codes are issued under the same NHI institution-code standard (醫事機構代碼); this repo's own `lib/server/facilities/sources/molHealthCheckFacility.ts:41` already uses `r.醫療機構代碼` as this source's `sourceId`. **This is exactly the (b) pattern the task asked about** — a stable institution code exactly matchable against a coordinate-bearing registry this repo already downloads for another purpose. Extending `backfillHospitals()`'s existing `codeMap` lookup to also cover `mol_labor_checkup` rows should require no new external dataset, just a second pass over an object this script already has in memory.

**#16 `health_check` / `mol_occupational_injury` — 職業傷病網絡醫院 (researched, none found — and the dataset itself has no code field).**

**#19 `green_shop` / `moenv_green_shop` — 綠色商店 (confirmed genuine gap — NOT covered by the existing opendata-geo backfill).**

## 3. Part 2 — Better free geocoding fallback for the genuine long tail

### 3.1 TGOS 全國門牌地址定位服務 (內政部地政司/國土測繪中心) — batch address-comparison service

**Not a bulk-downloadable dataset.** A `data.gov.tw` public suggestion thread (`data.gov.tw/suggests/21721`, "請開放800萬門牌位置資料") explicitly asks the government to open up the ~8 million national address-point ("門牌") records for direct download — as of this research, that request has not been fulfilled as a plain downloadable file. What **does** exist is TGOS's **批次地址比對服務 (batch address comparison service)**:

- **Access**: register as a TGOS member, then apply for the batch service; approval takes roughly 72 hours and returns an API key (confirmed via `gov.tw/News_Content_2_371654`). Open to government agencies, legal entities, academic units, and industry — not gated to government-only, per the same source.
- **Quota**: **10,000 address comparisons per day**, per registered user — raised from an original 500/day limit on 2015-07-01 (confirmed via `gis.rchss.sinica.edu.tw/qgis/archives/3458/`). This is roughly **4× the current combined OpenCage+Nominatim daily budget** (1,400 + 1,000 = 2,400, `geocodeBudget.ts:22-25`).
- **Delivery model**: asynchronous batch — submit a list of addresses, receive results via email notification with a download link, not a live per-request API. This is a **better fit for this repo's existing batch-job shape** (`geocodeBatch.ts`'s scheduled invocation model) than a rate-limited synchronous API, and structurally removes the "one slow request holds up the next" throttling problem that drives `MAX_FACILITIES_PER_INVOCATION` down to 8 (`geocodeBatch.ts:34`).
- **Source authority**: addresses are matched against the government's own 門牌 (house-number) registry rather than a general-purpose geocoder's fuzzy street/POI matching — plausibly higher precision for exactly the kind of Taiwan address strings this repo already struggles with (see the memory note on "inherent OpenCage road-name-ambiguity noise").
- **Coordinate system**: TWD97 by default, with an output coordinate-system choice per the HackMD writeup found (`hackmd.io/@aO674exYRgWnn1BgZhND9A/HkKjf0F15`) — would need conversion to WGS84 to match this repo's existing `lat`/`lng` columns (see `lib/server/facilities/geocodeProviders.ts:17` for the WGS84 Taiwan bounding box this repo already validates against).
- **Caveat**: the exact application requirements, any cost beyond the free quota, and whether it accepts programmatic (not just portal) submission were not fully confirmed in this research pass — the sources found describe the *existence and quota* of the service clearly but not every procedural detail. This would need direct contact with TGOS (the `News_Content_2_371654` page lists a contact phone number) or a hands-on registration attempt before committing engineering time.

### 3.2 Self-hosted open-source geocoder (Photon / Pelias) seeded with Taiwan OSM/address data

Researched as the alternative to "just add a third rate-limited free API":

- **Data source problem**: neither Photon nor Pelias invents new address coverage — both are typically seeded from OpenStreetMap data (optionally supplemented by "OpenAddresses" or "Who's On First" for Pelias). Since this repo's existing Nominatim fallback **already queries the OSM dataset live**, a self-hosted Photon/Pelias instance seeded from the same Taiwan OSM extract would very likely have **similar raw match/no-result characteristics** to what Nominatim already returns — the underlying address data doesn't improve just because the query path moves in-house. (No Taiwan-specific OpenAddresses coverage was found in this research pass to supplement OSM, unlike some other countries.)
- **What self-hosting *would* solve**: the actual root cause of the current pain is **rate limiting and shared-budget contention**, not primarily geocoder accuracy — `geocodeBudget.ts`'s whole design exists because both OpenCage and Nominatim's usage policies force an artificial ~1 req/sec throttle and hard daily caps. A self-hosted instance answers to no external usage policy — no daily cap, no throttle beyond what the host's own hardware allows. This directly attacks `MAX_FACILITIES_PER_INVOCATION`'s root constraint.
- **Engineering/hosting cost — likely prohibitive on this repo's current infrastructure.** Per this session's own memory of prior incidents on this exact host: it enforces a **768MB V8 heap cap** and previously crash-looped from a WASM-based renderer that couldn't fit inside it; it also has a hard **LVE process ceiling (20 Entry Processes)** that a 2026-08-23 NPROC-exhaustion outage traced to exactly 33 processes running at once. Both Pelias and Photon are typically deployed against an **Elasticsearch** backend, which alone commonly wants multiple GB of heap for even a small regional index — this is very unlikely to coexist with a shared cPanel host that already crash-loops under far lighter memory pressure. A workable deployment would need a **separate host** (a small VPS or container service dedicated to the geocoder), which is a materially different and larger cost than "add a third free API to the existing rotation." This should be weighed explicitly against §3.1's TGOS batch service, which needs no new infrastructure at all.
- **Recommendation**: self-hosting is not worth the engineering/infra cost right now, given (a) it doesn't obviously improve raw accuracy over the Nominatim data already in use, and (b) this host's documented memory/process constraints make it a genuinely separate infrastructure project, not a drop-in addition. §3.1's TGOS batch service is the higher-leverage next step to actually pursue — same "no new infrastructure" cost as OpenCage/Nominatim, ~4× today's combined quota, and a delivery model (async batch) that fits this repo's job shape better than another synchronous rate-limited API would.
